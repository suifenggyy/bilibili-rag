# 自动更新层级知识库 — 设计文档

日期：2026-06-23

## 1. 目标与范围

构建一个**自演化的层级知识库**：持续读取抓取的 Markdown 文档（含「正文」与「总结」），借助 LLM 智能识别其 topic 路径；通过不断录入文档，逐步完善 topic 层级；每个 topic 节点维护一份汇总该主题重点信息的 md 文档。

### 核心约束（已确认）

| 维度 | 决策 |
|---|---|
| 规模 | **A 小规模**：几十~几百文档，topic 树最终几十节点；整棵树可放入 LLM 上下文 |
| 文档归属 | **单一归属**：每个文档只属于一个叶子 topic |
| 树演化 | **B 增长 + 分裂**：只新增节点；叶子内容发散时分裂为子 topic（树自然加深），不做合并/重命名/移动 |
| 总结更新 | **A 全量重生成 + 每文档要点缓存**：用「所有缓存要点 + 新文档要点」重生成，不重读全文 |
| 分裂触发 | 文档数阈值粗筛 + LLM 复核（是否分、怎么分） |
| LLM 提供方 | 不绑定具体厂商；本设计只定义调用流程与 prompt |
| topic 命名 | **有区分度**：简洁、单一方向，不含「与/和/及/或」等并列词 |

本文档只做设计，不含实现。

## 2. 数据模型与存储结构

### 存储布局

以稳定 id + 索引文件为单一事实来源，避免分裂/重组时大改目录：

```
kb/
  index.json                 # 整棵 topic 树 + 元数据（单一事实来源）
  topics/
    <topic_id>/
      summary.md             # 该 topic 的汇总文档
      points/                # 仅叶子节点：每篇文档的要点缓存
        <doc_id>.md
  docs_raw/                  # 可选：原始抓取 md 归档
```

### index.json — topic 节点字段

| 字段 | 说明 |
|---|---|
| `id` | 稳定唯一 id（分裂/重组时不变，便于追踪） |
| `name` | 简洁、单一方向的名称（区分度核心） |
| `description` | 一句话边界说明——与兄弟节点的区别在哪（路由判断的关键依据） |
| `parent_id` | 父节点 id（顶层为 null） |
| `children` | 子节点 id 列表 |
| `is_leaf` | 是否叶子 |
| `doc_ids` | 叶子节点收录的文档 id 列表 |
| `doc_count` | 文档数（分裂阈值用） |

### 文档要点缓存 `points/<doc_id>.md`

录入时一次性抽取并存档，之后重生成总结时复用，不再重读全文。内容：标题/来源、一句话主旨、3~8 条要点。

### 关键设计点

路由判断不靠 name 猜测，而靠每个节点的 `description`（边界说明）。新建 topic 时强制约束 name 简洁单一，且 description 必须写清与兄弟的差异——这是保证「区分度」的机制。

## 3. 录入流程与分裂机制

### 单篇文档录入流水线

```
新 md 文档
   │
   ▼
[1] 要点抽取  ◀── LLM调用①
   │           输入：正文+总结  →  输出 JSON：要点列表 + 一句话主旨 + topic 提示词
   │           结果写入 points/<doc_id>.md (缓存)
   ▼
[2] 归属路由  ◀── LLM调用②
   │           输入：整棵 topic 树(name+description) + 本文要点
   │           输出 JSON，三选一：
   │             • existing   → 命中已有叶子 {topic_id}
   │             • new_child  → 在某节点下新建叶子 {parent_id, name, description}
   │             • new_root   → 树为空或完全无关，建新顶层 {name, description}
   ▼
[3] 落库  ── 程序更新 index.json：写 doc_id、doc_count++；新建节点则建目录
   │
   ▼
[4] 叶子总结(重)生成  ◀── LLM调用③
   │           输入：该叶子下「所有缓存要点」(含新文档)
   │           输出 Markdown  →  覆盖 summary.md
   ▼
[5] 分裂检查  ── 程序判断 doc_count ≥ 阈值N ?
        │否 → 结束
        │是 ▼
      [6] 分裂复核+重分配  ◀── LLM调用④
                  输入：该叶子全部要点
                  输出 JSON：是否分裂 / 子 topic 划分(name+description) / 每篇文档归到哪个子 topic
                  │
            ┌─────┴─────┐
          不分裂        分裂
          (结束)         ▼
                  程序重组：原叶子升为父节点；按方案建子节点、迁移 points 缓存
                  ▼
                  对每个新子节点跑 [4] 生成 summary.md
                  父节点 summary.md 改为「子节点概览」(LLM调用⑤，轻量，可选)
```

### 关键约定

- **路由只在叶子落地**：`new_child` 也是建叶子；中间层只在分裂时产生。保证文档永远挂在叶子上，模型简单。
- **分裂阈值**：`doc_count ≥ N`（建议 N=8~12，可配置）只做粗筛；真正分不分、怎么分由 LLM 调用④决定。LLM 判断「主题未发散」时可拒绝分裂（此时可把该叶子阈值临时抬高，避免每篇都复核）。
- **要点缓存复用**：调用③④只吃缓存要点，不重读全文，控制 token。
- **区分度兜底**：调用②新建节点、调用④分裂时，prompt 都强制——子节点之间 description 必须互斥、name 单一方向；程序侧再校验 name 是否与兄弟重复。
- **父节点概览**（调用⑤）非必需，可先用模板（罗列子节点 name+description）代替，省一次 LLM。

## 4. LLM 调用 Prompt

> 约定：决策类（②④）返回 JSON，生成类（①③⑤）返回 Markdown。`{{...}}` 为程序注入的变量。

### Prompt ① 要点抽取

```
你是知识库的要点抽取助手。请阅读以下抓取的文档，提炼其核心信息，供后续归类与汇总使用。

【文档正文】
{{body}}

【文档原始总结】
{{summary}}

请输出 JSON：
{
  "subject": "用一句话(≤30字)概括本文主旨",
  "key_points": ["要点1", "要点2", "..."],   // 3~8 条，每条为完整可独立理解的陈述句
  "topic_hint": "你认为本文最贴切的单一主题方向(简洁名词短语,单一方向,不含'与/和/及')"
}

要求：
- 要点须是事实/结论/方法，去掉套话和背景铺垫。
- topic_hint 必须聚焦单一方向，例如"显存带宽优化"而非"显存与并行优化"。
```

### Prompt ② 归属路由

```
你是知识库的分类路由器。已有一棵层级 topic 树，请判断新文档应归入哪个叶子主题，或是否需要新建主题。

【现有 topic 树】(缩进表示层级；每行: id | 名称 | 边界说明)
{{topic_tree_text}}

【新文档要点】
主旨：{{subject}}
要点：
{{key_points}}

判断规则：
1. 若某个【叶子】主题的边界明确覆盖本文，选 existing。
2. 若本文方向属于某个已有节点之下、但没有合适叶子，选 new_child，在该节点下新建叶子。
3. 若与整棵树都不相关，选 new_root。
4. 宁可新建，也不要勉强塞进边界不符的主题（保持区分度）。

新建主题(new_child/new_root)时：
- name：简洁、单一方向、不含"与/和/及/或"等并列词；不得与同级已有节点重名或语义重叠。
- description：一句话写清"本主题收录什么、不收录什么"，必须与同级兄弟主题边界互斥。

输出 JSON(三选一)：
{ "decision": "existing", "topic_id": "...", "reason": "..." }
{ "decision": "new_child", "parent_id": "...", "name": "...", "description": "...", "reason": "..." }
{ "decision": "new_root", "name": "...", "description": "...", "reason": "..." }
```

### Prompt ③ 叶子总结（重）生成

```
你是知识库的主题汇总员。请基于该主题下所有文档的要点，生成/重写该主题的汇总文档。

【主题】{{topic_name}}
【主题边界】{{topic_description}}

【本主题下全部文档要点】
{{all_points_concat}}   // 每篇: 主旨 + 要点列表

请输出一篇 Markdown 汇总文档，结构：
# {{topic_name}}

> 一句话定位本主题(对应主题边界)

## 核心要点
- 跨文档归纳、去重、合并同类项后的关键结论(而非简单罗列每篇)

## 细分内容
按子方向组织要点；若出现明显的多个子方向，在对应要点后标注，便于后续判断是否需要拆分。

## 待补充/存在分歧
列出文档间矛盾或覆盖不足之处(没有则写"无")。

要求：忠于要点、不杜撰；合并重复信息；保持简洁。
```

### Prompt ④ 分裂复核与重分配

```
你是知识库的主题治理员。某叶子主题积累的文档较多，请评估它是否已"主题发散"需要拆分。

【当前主题】{{topic_name}}
【主题边界】{{topic_description}}
【收录文档要点】(每篇带 doc_id)
{{points_with_docid}}

第一步：判断是否需要拆分。
- 仅当存在 2~4 个边界清晰、相互独立的子方向时才拆分。
- 若内容仍聚焦同一方向，不要拆分。

第二步(若拆分)：设计子主题并把每篇文档分配进去。
- 子主题 name：简洁、单一方向、不含并列词，彼此不重叠。
- 子主题 description：边界互斥，能解释为何某些文档归此而非彼。
- 每篇文档必须且只能分到一个子主题。

输出 JSON：
{ "split": false, "reason": "..." }
或
{
  "split": true,
  "reason": "...",
  "children": [
    { "name": "...", "description": "...", "doc_ids": ["...","..."] },
    { "name": "...", "description": "...", "doc_ids": ["..."] }
  ]
}
要求：children 的 doc_ids 必须恰好覆盖全部输入文档，无遗漏无重复。
```

### Prompt ⑤ 父节点概览（可选，轻量）

```
为以下父主题生成一段简短导览，说明它包含哪些子主题、各自负责什么。

【父主题】{{topic_name}}
【子主题列表】(名称 | 边界说明)
{{children_list}}

输出 Markdown：
# {{topic_name}}
> 一句话定位

## 子主题
- **{{子名}}** — {{该子主题收录范围, 一句话}}
(逐个列出)
```

## 5. LLM 调用汇总

| 调用 | 时机 | 输入 | 输出 | 是否每篇都调 |
|---|---|---|---|---|
| ① 要点抽取 | 每篇录入 | 正文+总结 | JSON 要点 | 是 |
| ② 归属路由 | 每篇录入 | 整树+要点 | JSON 决策 | 是 |
| ③ 叶子总结 | 落库后 | 叶子全部缓存要点 | Markdown | 是（命中/新建叶子时） |
| ④ 分裂复核 | doc_count≥N | 叶子全部要点 | JSON 分裂方案 | 否（仅超阈值） |
| ⑤ 父节点概览 | 分裂后 | 子节点 name+desc | Markdown | 否（可用模板替代） |

稳态下每篇文档约 3 次 LLM 调用（①②③）；触发分裂时额外 ④ 与若干次 ③。
